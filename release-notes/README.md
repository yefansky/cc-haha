# 从提交生成更新日志

提交格式以根 `AGENTS.md` 的“提交与更新日志规范”为准。标题采用[约定式提交](https://www.conventionalcommits.org/zh-hans/v1.0.0/)，正文写清改动、原因、解决的问题和供用户阅读的更新说明。生成器参考 [conventional-changelog](https://github.com/conventional-changelog/conventional-changelog) 的按提交类型分类流程；这里的中文字段校验、已发布版本选择和包体接线由本仓库脚本实现，没有引入新的依赖，也不调用模型替作者编造说明。

## 发布时发生什么

1. Windows 主干持续发布先计算版本号，读取同渠道已经公开发布、带自动更新文件且属于当前提交历史的最近版本。
2. `scripts/release-changelog.ts` 读取该版本之后的所有普通提交，包含合并进来的分支提交，不重复列合并提交；只发布各提交的“更新日志”字段。格式不合格会失败并显示提交编号。上一次打包失败或仍是草稿的版本不会成为起点，避免漏掉尚未发布的改动。
3. 当次版本说明写入 `release-notes/v版本.md`、`desktop/public/CHANGELOG.md` 和 `desktop/build/release-notes.md`。`desktop/public/changelog.json` 同时保存当次说明和完整版本历史。
4. 前端构建把版本和内容直接编译进应用，也把可独立阅读的日志文件复制进包内 `dist/`。发布构建缺少日志、内容为空或版本不一致会报错；普通开发运行允许没有日志并显示明确提示。
5. 桌面打包器按其标准 `build/release-notes.md` 约定，把说明写入 `latest*.yml` 自动更新文件。发布前再次核对版本与内容必须和包内日志完全一致。
6. 发布页面使用同一份版本说明；Windows 发布先上传完整草稿，再转为公开版本。标签触发的多平台发布只生成一次，通过构建产物分发到全部平台和最终发布步骤，避免各平台取到不同发布范围。

用户在关于页面看到“新版更新内容”“当前版本更新内容”和“历史版本更新记录”。新版说明来自更新检查结果；当前版本和历史说明来自包内数据，更新后、重启后、断网时都能阅读。顶部“更新日志”跳到当前版本说明；“查看所有版本的更新记录”定位到应用内历史区域，不打开网站。历史按版本从新到旧排列，可按版本号或改动内容搜索、展开阅读，每次增加显示五版。

旧安装包必须先安装包含此功能的新包，才能使用包内历史展示。当前版本缺少日志时仍明确提示，不拿历史记录或最新版本冒充当前版本说明。

## 本地检查与首次接入

```powershell
bun run scripts/release-changelog.ts --check-message path/to/commit-message.txt
bun run scripts/release-changelog.ts --from v0.6.100 --version 0.6.101 --dry
```

第二条是范围预览示例，请替换为真实的已发布起点和目标版本。移除 `--dry` 才会写文件。GitHub 工作流自动设置仓库名和访问令牌；本地让工具选择发布起点时，设置 `GITHUB_REPOSITORY` 为目标仓库并使用已登录的 `gh` 命令。

首次接入也可以通过本地环境变量 `CC_HAHA_CHANGELOG_FROM` 或手动工作流的 `changelog_from` 输入明确起点；正常发布留空，始终自动选取已发布版本。

首次发布若没有同渠道已发布祖先版本，必须通过 `--from` 明确起点；工具不会把全仓历史误写为一次更新。历史英文提交若出现在待发布范围，先核对范围和真实改动再整理，不自动重写已公开提交。手工旧版说明仍留作历史记录，新发布流程以提交生成的内容为准。`scripts/release.ts` 在版本提交前调用生成器落盘，最终发布包含版本提交本身的维护说明。

保留现有持续发布的版本编号规则。此功能不更改版本大小比较，也不会让已安装的历史高版本自动降级。

## 验证边界

`scripts/release-changelog.test.ts` 用临时 Git 仓库验证发布范围、合并、草稿、重跑、不合格提交、中文表达和产物一致性。关于页面测试驱动真实更新状态操作，验证更新前、下载后和重启后的说明。真实安装升级仍须在明确发布后，用生成的安装包实际验证。

## 历史补录与长期保存

`release-notes/history.json` 保存已核对的 41 个公开版本，从 0.5.3 至 0.6.47。日期和目标提交来自 yefansky/cc-haha 的已发布版本；说明依据各版本的提交及代码差异整理，标记为“历史补录”。它们是回补摘要，不是当年的原始发布正文，也不代表重新运行过全部旧安装包。不存在的发布号不补造。0.6.11 重放过旧提交，采用与前一版本的实际文件差异，避免重复宣称新增功能；来源提交和对比方式保存在数据中供维护者核对。

这份早期补录是历史英文提交的明确例外，不修改已公开提交。后续版本继续严格从合格提交的“更新日志”生成；不要手写新版本说明绕过提交校验。修订补录时，先核对原版本证据，再修改对应条目，保持完整中文和具体用户变化。

两条发布工作流都会把 `changelog.json` 作为发布附件上传。下次生成先读取已发布的历史附件，再合并仓库中的早期补录与本次说明；相同版本只保留一条。并行打包造成历史缺口时，按生成时已经公开的版本补齐其他归档。已存在的归档下载失败、格式错误或与版本不符会中止发布，避免悄悄丢失历史。早期未提供附件的版本使用经过核对的补录。归档反映构建时已公开的版本，构建开始后才发布的其他版本会在后续包中补入。

普通开发构建也会嵌入早期补录。正式发布必须生成与应用版本一致的当前说明和有效历史；本地仅用 `--from` 且未设置 `GITHUB_REPOSITORY` 的生成属于本地预览，只包含仓库补录与本次内容。正式工作流会自动设置仓库名并下载已发布归档。
